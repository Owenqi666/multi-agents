# verify

在仓库根目录运行：

```bash
scripts/verify.sh
```

这个脚本是唯一的检查入口，git hook 和 CI 调的也是它。检查命令只写在脚本里，这样三处永远跑同一套东西。要增减步骤就改脚本，不在别处另写一份。

## 结果处理

- **全部通过**：用一行报告跑了哪些步骤。
- **有步骤失败**：报告失败的步骤名和最后 20 行输出，修掉原因后重跑。调试时可以用 `scripts/verify.sh <步骤名>` 只跑失败的那步，提交前仍要完整跑一遍。
- **环境问题**（找不到 `uv`、没有 `pyproject.toml`）：原样报告，不绕过。唯一的例外是项目骨架建好之前：仓库里还没有任何 Python 代码时，照常提交，并在报告里注明没有跑检查。

## 检查挡住你的时候

检查存在的意义是拦住回归，所以它变红时该改的是代码。不要为了变绿去削弱、跳过或删除测试和回放场景，不要放宽 lint 或类型检查的配置，也不要用 `--no-verify` 提交。

如果你判断是检查本身错了（测试断言的是错误行为、场景已经过时），停下来说明理由，交用户决定。

## 什么时候可以不跑

只改了文档（`*.md`）时可以不跑。只改测试或回放场景时照常运行，因为改坏测试和改坏代码一样会让检查失去意义。
