# state-change

状态机的正确性靠三样东西保持一致：转移表、表结构、回放场景。只改其中一样，留下的往往是"旧尝试的结果覆盖了新尝试"这种只在并发和重试时才出现的错误，普通单元测试测不出来。所以三样在同一次改动里一起动。

## 先对齐概念

以 `PROJECT_PLAN.md` 为准：运行、任务、阶段、尝试、会话；审核另有快照、审核轮次、席位。一个席位在一个审核轮次里可以有多次尝试，只有当前尝试的终态能推进审核。计划里没有的概念，先和用户确认再引入。

## 流程

1. **先改转移表。** 所有合法转移集中登记在 `src/multi_agent/core/transitions.py`（还没有这个文件就按此创建）。新状态、新事件只在这里登记。其他模块不写"如果状态是 X 就…"的分支来绕开它，没登记的转移直接抛错。
2. **表结构变化写迁移。** 在 `src/multi_agent/store/migrations/` 新增一个编号递增的迁移文件。已经提交的迁移不改、不删，因为已有的数据库是按它们建出来的。
3. **补回放场景。** 在 `tests/replay/scenarios/` 新增或修改场景，并确认它在改动前失败、改动后通过。场景的要求见下文。
4. **新增失败分类**时，同时更新分类枚举、适配器里的映射，以及至少一个产生该分类的场景。现有分类：认证失效、限流、模型不可用、超时、取消、越界补丁、测试失败、集成冲突。
5. **跑检查。** 先 `scripts/verify.sh unit replay`，提交前完整跑 `scripts/verify.sh`。

## 回放场景的要求

- 输入是一串带顺序的合成事件，每条注明来自哪个尝试、哪个席位。不调用真实 CLI，不依赖真实时间。
- 断言两样东西：最终状态，以及历史里留下了什么。只断言最终状态，会漏掉"晚到结果被丢弃而没进历史"这类问题。
- 同一个场景重复运行，结果相同。

阶段 0 的四个基线场景任何时候都保持通过，不删、不放宽：

| 场景 | 要守住的行为 |
| --- | --- |
| 两个席位并行 | 两份报告齐全才进入整体评估，一方先完成不推进 |
| 同一快照补跑 | 只重开失败的席位，沿用原席位配置，已成功的报告保留 |
| 旧尝试迟到 | 晚到的终态只进历史，不覆盖当前尝试的结果 |
| 取消 | 以回合终态或进程停止为依据，已有记录保留 |

## 写终态的规则

- 检查"该尝试仍是当前尝试"和写入终态放在同一个事务里。分开做，两步之间就可能插进一次重试。
- 代码修订后生成新快照，旧报告继续关联旧快照。
- 重启后先展示可恢复的阶段。重新派发前检查上次尝试和工作区里的结果。

## 交付说明里列出

新增或修改的状态和事件、迁移编号、新增的场景名，以及哪些已有场景因此改动、为什么改。
