## hang-start 仍覆盖真实 0.4 秒超时

两个 provider 的 hang-start 都先等待假进程写入 `FAKE_HANG_READY` 指定的标记，核对 capture 中的 hang-ready PID 恰为当前 `state.process.child.pid`，且子进程仍在运行、真实 deadline 尚未到期。启动等待独立受 `asyncio.timeout(3)` 限制。

确认实际到达挂起点后，测试将同一个真实 asyncio deadline 重定时到当前 loop time + 0.4 秒，再消费生产 adapter 事件与结果；断言至少经过 0.4 秒，最终为 TIMEOUT、唯一终态，实际进程已退出，最后两个事件为 Error、ProcessExited。结果等待与失败时清理也各有 3 秒上限，清理只作用于该次持有的 task/process。最终 finally 在取消 task 后用 `asyncio.wait(timeout=3)`，断言无 pending，再读取 `task.result()`，不会以 `return_exceptions=True` 吞掉清理失败。既有假挂起行为保留，新增同步不会用预检耗尽预算来冒充挂起阶段覆盖。

## 慢启动回归的因果证据

新增 `test_slow_version_reaches_model_error_after_old_timeout` 仅设置假 CLI 的 `FAKE_VERSION_DELAY=0.6`，仍用 3 秒总预算。配置余量为 `3 - 0.6 = 2.4` 秒；这是配置差值，不是对真实剩余时间或机器调度的保证。

该测试通过 RuntimeAdapter 的实际子进程路径运行，并精确断言 fake capture 中只有一条 `version-delay`、其 seconds 为 `0.6`，再核对原始记录中的两个 spawn：`--version` 与 `app-server --strict-config`。version 自然 exit 0，spawn 到 exit 大于旧窗口 0.4 秒，且这段 version 生命周期没有 signal。随后 AppServer 确实收到一次 `turn/completed`，`turn.status=failed`、`error.codexErrorInfo=modelNotFound`，最终结果精确为 `MODEL_UNAVAILABLE`，保留唯一终态与实际 ProcessExited 顺序断言。AppServer 终态后的正常 SIGTERM 清理不被误禁。
