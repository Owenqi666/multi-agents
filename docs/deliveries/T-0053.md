# T53 测试可执行文件大小边界修复

开发基线为 `2b2b85d5691b5540956db96559402f5a75745423`。用户要求修复探测器与产品入口的大小上限不一致，保留原失败和现有检查，并在检查后直接复验最后一项零模型验收。

## 问题与修复范围

第一次 S9 的 `native-test-boundary` 在任何 runtime 或命令启动之前失败：固定 Codex 0.169.0 二进制为 280,704,736 字节，超过 `test_probe._binary_hash` 的 256 MiB 上限。独立复核又发现 `TaskTestRuntimeAdapter._check_executable` 同样限制 256 MiB，因此只改探测入口仍不足以运行。产品 `capture_task_test_policy` 既有上限为 512 MiB。

本卡仅将探测器和测试运行时两处上限对齐到既有 512 MiB。文件类型、身份、稳定性、完整流式哈希、实际版本、权限配置和停止检查保持。独立回归跨三个入口检查实测二进制大小、恰好 512 MiB、超过上限一字节；稀疏文件头尾是非执行内容，不启动程序或接触真实认证。

## 复核与证据保留

Claude 工具关闭的卡片文字复核实际报告 `claude-opus-5-5`、completed、退出 0；实际 effort 未报告。这是开发复核，独立于零模型实机验收。意见落实为：基线 red 仅要求接受尺寸的两个旧门禁失败；三函数只做本地检查，不调用运行入口；原生运行后源码/测试冻结，仅更新文档，最终提交须与实际 source_hashes 相同。

原 S9 的三个成功复核 case、测试入口失败、两份计划和所有日志保留。仓库外 `phase-two/T53/prior-evidence-preservation.json` 记录原目录 69 个文件的哈希，交付时复核文件集合与字节均不变。旧报告仍绑定旧提交，不改写为本卡重跑结果。本卡不重复之前的两个模型 case。
