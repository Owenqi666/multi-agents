# 版本项目书 · 项目计划、阶段开发与可选委派

评估基线为 2026-11-19 的 `main@b9dff65`。PM 确认最终目标后，由 Astra 这一档的模型制定项目计划。Sol 每次承接一个阶段。用户可以让 Sol 完成整个阶段，也可以启用 Terra / Sonnet 这一档，由 Sol 拆分后委派。T-0062 提供基础网页与本地桥。当前主分支只有其开发契约。[前端任务书](../tasks/T-0062-local-web-workbench.md)

**交付目标。** PM 能在本地网页上把一次需求推进到已验证的阶段交付，随时查看“为什么这样设计、谁在做哪一段、哪个版本已经通过测试和审核”。既有工作台阶段 3 已收尾，本项目书描述其上的一次产品更新。下文的“阶段”由工作台为用户的目标项目生成，数量与边界由目标决定。[既有工作台项目书](../PROJECT_PLAN.md)

**本次开发分工。** GPT-6.2 Sol（ultra）开发窗口按功能任务卡实施并提交。本窗口的 Astra 负责规划、复核契约、审核候选、反馈修正，以及在最终提交上核验整个更新。用户已提前批准本更新所需的真实模型调用。产品中的模型与推理档位仍由 PM 选择。

## 一、从 PM 的想法到项目计划书

1. **需求澄清。** PM 可以直接确认清晰的目标，也可请 Astra、Fable 或两者结合仓库基线完善输入。单顾问给出草案。双顾问由一方起草、另一方对照原话和基线查漏。界面给 PM 一份可编辑目标，说明有依据的背景、假设和需要决定的取舍。咨询结束后由 PM 决定是否进入项目规划。
2. **项目规划。** 项目规划者默认示例为 Astra，可由用户选择同档角色。它读取 PM 确认的目标，交付一份可阅读的项目计划书及其阶段任务书。计划写明整体架构、共用接口和实施顺序。每个阶段分别写明要交付的功能、实现方向、流程、依赖、验收样例和交给下一阶段的产物。阶段数随项目而定。计划正文与网页阶段列表取自同一版本，方便 PM 查看、修改和追溯。
3. **领取阶段。** Sol 每次领取一个当前阶段。工作台交给它项目计划版本、已确认目标、相关全局约束、当前阶段任务书，以及已满足的上游交付和基线。其他阶段的摘要供理解接口使用，本次写入范围只覆盖当前阶段。

## 二、每个阶段的两种开发方式

| PM 对当前阶段的选择 | Sol 的职责 | 实施与交付 |
| --- | --- | --- |
| **Sol 直接开发**，建议作为初始选项 | 把阶段任务书落实为一份可执行的阶段任务卡，按阶段目标开发并交付。Sol 可以自行安排内部步骤。 | 通过既有任务卡复核后，由 Sol 使用实施权限写代码，交付阶段候选。工作台无需生成小阶段卡，也不会为此启动 Terra 或 Sonnet。 |
| **委派给 Terra / Sonnet** | 将这一个阶段细化为若干可独立验收的小阶段，明确每项输入、输出、接口、写入范围、依赖和验收条件。Sol 负责阶段内的接口和结果衔接。 | 每次实施会话只领取一个已复核的小阶段、一张卡。执行者同时获得相关架构决定与阶段目标。独立且写入范围互不重叠的小阶段可用现有批量运行，有依赖的按顺序执行。工作台归集候选并核对阶段验收。 |

PM 可以在同一个项目里让第一阶段由 Sol 开发、第二阶段启用委派。选择实施模型要满足该阶段或任务卡的冻结项目规则。若阶段强制 `frontend/**` 由 Claude 实现，页面应在派发前说明 Sol 直接开发与该规则的冲突，并让 PM 主动选择兼容的分工。只选 Terra 或 Sonnet、查看计划、刷新页面均不会额外触发需求咨询。独立小改动仍可走既有单任务入口，已有可派发的任务卡可直接使用。

以账单工作台为例。Astra 将项目分成“导入并持久化账单”“分类与查询”“按月生成报表”三个阶段。第一阶段关闭委派时，Sol 交付从 CSV 导入到查询已保存账单的完整功能。若开启委派，Sol 可以先定义交易记录格式和存储接口，再开出“解析 CSV 并报告错误行”和“将有效记录入库并验证可查”两个小阶段。一次 Terra 会话只领其中一项。最终用同一份 CSV 验收第一阶段。第二、三阶段仍保留在项目计划中，尚未展开为实施卡。

## 四、接入现有工作台的约定

- **计划与代码证据的关系。** 记录“确认目标版本 → 项目计划版本 → 阶段 → 阶段卡或小阶段卡 → 候选及验收结果”。计划书可先拟好后续阶段，后续阶段的执行基线在领取时根据已交付的依赖确定。PM 改目标或计划时保留原版本，已完成阶段保留原证据，受影响的待执行工作关联新版本。阶段完成以可观察的交付物和验收结果为依据。产生计划或生成全部小卡均不表示阶段已完成。现有显式接受与合并仍由用户触发。[集成和接受流程](phase-three-development.md)
- **复用实施与审核。** 目前的规划提示一次只产出一张卡，CLI、输入校验和状态转移也绑定了 Claude 起草、Codex 复核。新角色需要同步更新这些入口及旧记录读取。实施、依赖检查、具备条件的任务并行、测试和审核复用已有机制。目标澄清、项目计划、任务卡复核和最终代码审核各自有明确产物。审核者根据冻结候选和验收条件独立出结论。[规划提示词](../src/multi_agent/cli/planning_prompt.py) · [规划输入校验](../src/multi_agent/cli/planning_inputs.py) · [状态转移](../src/multi_agent/core/transitions.py) · [批量实施与交付](phase-three-development.md)
- **模型及提示词。** 沿用 T-0062 的 Astra、Sol、Terra、Fable、Opus、Sonnet 六个家族。Luna、Haiku 不进入新任务或备选菜单。角色、型号与推理档位分别设置，保留具体型号支持的 `low`。由工作台按本阶段方式组装职责、目标、接口和验收上下文，请求配置与运行时报告分开显示。每张卡可选择获准的实施者。一次批量运行中为各卡分别传不同的显式配置，可另列增量。首版可以单卡派发或沿用按项目规则选择的批量运行。[前端模型约定](../tasks/T-0062-local-web-workbench.md#首版模型选择范围) · [派发规则](../src/multi_agent/core/dispatch.py) · [实施提示词](../src/multi_agent/cli/task_prompt.py)

## 五、版本验收

1. PM 直接确认目标或使用顾问后编辑确认。Astra 在该版本上生成可读的项目计划书。以三阶段样例核对每个阶段的目标、实现方式、流程和验收。刷新后可打开同版计划，尚未领取的阶段没有实施尝试。
2. 在规则允许的阶段关闭委派。假 CLI 记录的实施者只有 Sol，Terra 与 Sonnet 的实施调用均为零。没有为该阶段生成小阶段实施卡，Sol 的候选通过该阶段的测试与审核。正式卡复核和代码审核可使用用户配置的独立模型。
3. 在另一阶段启用委派。Sol 仅展开选中的阶段，至少生成两张各自可验收的小阶段卡。检查每次 Terra 或 Sonnet 实施的卡号、写入范围、父阶段和项目计划版本。一项未完成时，页面能显示已交付项和阻塞项。阶段验收成功后可追溯参与的候选和测试证据。
4. 对照角色规则、版本和兼容性。显式执行者与项目路径规则冲突时应说明来源。项目计划修订后，旧候选仍能打开原计划。现有已审核单卡直派、同轮补跑及原有单审或双审继续按冻结输入运行。

## 六、操作入口与数据交接

CLI 与本地网页调用同一组领域操作。下表约定输入和可见结果，具体命令名称、参数、持久化实现由对应任务卡固定。网页继续通过 T-0062 的本地桥提交耗时作业并读回结果。领域运行 ID 与网页作业 ID 分开保存。[网页与桥接口](../tasks/T-0062-local-web-workbench.md#3-浏览器与本地桥的-http-契约待实现)

| 用户操作 | 输入 | 持久化结果及下一步 |
| --- | --- | --- |
| 编辑和确认目标 | 仓库及基线、用户原话、可选咨询意见、用户确认文本 | 保存可独立引用的目标版本。新一轮规划只读取选择的确认版本。 |
| 生成和查看项目计划 | 目标版本、规划模型及档位、同一仓库基线 | 保存可读计划、结构化阶段、依赖和运行证据。根据项目计划版本可以重开原文和阶段目录。模型失败时保留失败原因。 |
| 开始一个阶段 | 项目计划版本、阶段标识、基线与上游交付、阶段方式和角色配置 | 直接方式产生一张阶段卡。委派方式产生一组归属该阶段的小阶段卡。复核结果对应具体卡，每次实施只消费获准的卡及其上下文。 |
| 跟踪、核验并进入下一阶段 | 阶段标识及关联的 task、candidate、integration、review 标识 | 汇总已完成、待处理和阻塞的交付，支持回看日志与证据。上游交付变化时按现有依赖和候选语义确定下游可用基线。 |

## 七、实施顺序与审核交接

| 顺序 | 交付给 PM 的可用能力 | 审核入口 |
| --- | --- | --- |
| 1 · 项目计划 | T-0063 首先贯通确认目标、调用真实规划运行时、保存项目与阶段计划及 SQLite 版本、从 CLI 查看指定版本。 | 主窗口使用同一份样例核对目标、阶段、依赖与证据，重新启动命令仍能读回。 |
| 2 · 阶段直做和委派 | 先让 Sol 在一个阶段完成写入和候选交付，再用另一阶段验证 Sol 一次拆出多卡、每位执行者一次只领一张。 | 复用同一项目，比较两种方式的实际模型调用、阶段归属、候选、测试和独立审核。 |
| 3 · 顾问与网页 | 接入单顾问和双顾问、编辑确认，以及网页对阶段模式、模型、证据和历史的操作。优先复用已经交付的 T-0062 页面与桥服务。若仍只有契约，开发窗口按该契约实现本次更新所需的入口和读回，保留其余 T-0062 功能原有的交付安排。 | 从空白页面完成一次项目规划，走通两种阶段方式。刷新或重启后能定位到原计划与候选。 |
| 4 · 版本验收 | 在最终候选执行完整检查、真实模型与浏览器验收，修复阻塞后，在修订提交上重跑受影响路径。 | 主窗口逐项对照第五节的验收行为和本节证据完成技术审核。用户保留最终接受与合并权。 |

每个可独立使用的功能对应一张实现卡。开发窗口提交时记录开工与候选 SHA、已运行的完整 `scripts/verify.sh`、逐项验收、实机证据位置和已知限制。主窗口按实际可操作功能汇报进度，真实模型及档位只记运行时报告值。版本收尾时核对两条阶段开发路径、旧流程兼容和真实浏览器操作，交付最终候选、启动方式和验收回执。
