### 接力线的步骤和数据来源

新后端把工作分成两层：项目层（需求咨询、确认目标、项目计划）和阶段层。阶段有两种模式：直接模式由 Sol 拟一张卡并自己实施；分派模式由 Sol 拆成几张子卡，每张由 Terra 或 Sonnet 实施，最后由工作台合并。接力线按下表画，「读哪里」写的是 `GET /api/resources/{kind}/{id}` 返回的 `data` 下的字段。

| # | 步骤 | 持有者 | 读哪里 | 完成的标志 |
| --- | --- | --- | --- | --- |
| 1 | 需求顾问 | Astra、Fable，1 到 2 位，依次进行，第二位能读到第一位的意见（不是盲审） | `consultation` 的 `seats[i]` | `seats[i].status` 为 `succeeded` |
| 2 | 确认目标 | 你 | `goal` 的 `confirmed_at`；有咨询时 `consultation.adoption` 为 `accepted`（原样采纳）或 `edited` | goal 存在 |
| 3 | 项目计划 | Astra 或 Fable；你手改计划时持有者是你 | `project-plan` 的 `status`、`planner_request`、`evidence` | `status` 为 `succeeded` |
| 4 | 领取阶段 | 你，工作台检查前置阶段 | `project-stages` 的 `stages[]` | 阶段记录存在 |
| 5 | 拟卡或拆分 | Sol | `stage` 的 `planning.attempts.draft[-1]`；拆分时 `planning.planning_kind` 为 `stage_split` | 直接模式 `planning.card` 非空；分派模式 `split_verified` |
| 6 | 卡片复核 | 默认 Opus，不能和 Sol 同一个模型 | `planning.attempts.review[-1].runtime.result`；分派模式每张子卡各一份，复核人沿用阶段的设置 | `planning.phase` 为 `ready` 或 `bound`；子卡看 `leaves[i].review_ready` |
| 7 | 实施 | 直接模式 Sol；分派模式每张子卡 Terra 或 Sonnet，可以并行，`unmet_dependencies` 非空的子卡等待 | 直接模式 `implementation`；分派模式 `leaves[i].implementation`，执行者取 `leaves[i].planning.draft_projection.executor` | `candidate_verified` |
| 8 | 合并 | 工作台，只在分派模式 | `integration` | `integration.candidate` 非空 |
| 9 | 测试 | 工作台，跑登记过的命令，不用模型 | 直接模式 `implementation.tests[]`；分派模式 `integration.evidence.test` | `tests_passed` |
| 10 | 代码审核 | 1 到 2 席，两席同时开始、互不可见，模型不能相同 | 直接模式 `implementation.reviews[]`，去掉 `metadata.kind` 为 `confirmation` 的确认轮；分派模式 `integration.evidence.reviews[-1]` | `review_satisfied` |
| 11 | 返工 | 原实施者，最多一次 | 直接模式是实施记录里 `request.kind` 为 `task_rework_started` 的那次尝试；分派模式是 `integration.evidence.rework`，成功后生成一个子集成 | 复审后 `review_satisfied`，线合回第 9 步 |
| 12 | 接受 | 你 | 分派模式 `integration.evidence.acceptance`；直接模式的阶段没有这个字段 | `accepted_at` 非空 |

- 模型名和推理档位只显示运行时报告的值：咨询席位和计划在 `evidence.reported_model`、`evidence.reported_effort`，拟卡、复核和实施的尝试在 `runtime.reported_model`、`runtime.reported_effort`，审核席位在 `seats[].attempts[]`。为 null 时显示「未确认」。请求的模型单独标「请求」，不拿来顶替报告值。
- 第 12 步不影响后续阶段解锁，后续阶段只看 `review_satisfied`。直接模式的阶段到审核通过为止；要把它的候选合进目标分支，另走 `integration.create`、测试、审核、接受，舞台把这几步画成同一条线的延长段（建议）。
- 作业运行期间读 `stage` 会抢仓库锁（见「读回与仓库锁」），所以舞台在作业期间按作业的 `action` 判断交接物停在哪一步，席位状态读不抢锁的 `review`，需求咨询、项目计划和阶段列表照常读。阶段本身等作业结束后再读一次。
- 一个作业可能走过好几步：直接模式的 `project.stage.start` 包含拟卡、复核和实施；开着自动返工的 `task.review`、`integration.review` 可能包含返工、重测和复审。舞台在作业结束后按读回补画中间各步。
- 时长：审核席位有每次尝试的开始和结束时间，咨询席位和计划有 `started_at`、`finished_at`；拟卡、复核、实施只有开始时间，结束时间要读 `plan` 或 `task` 的 `history=1`；测试没有时间。
- `blocked_reason` 里也会出现进度文字（例如 `waiting for ...`），不全是错误。`dispatch_error` 出现后一直保留。
- 席位键：任务审核是 `reviewer-1`、`reviewer-2`，集成审核是 `seat-1`、`seat-2`。网页按 `seats[].key` 显示，不写死。
- 修订后的计划在 `project-stages` 里只列在它名下领取的阶段，沿用源计划的阶段顺着 `dependencies[].stage_run_id` 找回。
- 未领取的子卡没有 `implementation_attempt`、`planning`、`implementation` 三个键，按 null 处理。分派阶段的 `integration` 每次读取时按成员重新匹配，ID 可能换成更新的那个。

## 接口条件

下面写的是后端 `77991ab` 已带的本地 HTTP 服务（`src/multi_agent/web/`，T-0067、T-0068）的实际行为，加上桥一侧要补的部分。标「补 N」的条目是新做的，编号对应「桥接服务要补的内容」一节；没有标的是现有行为，网页现在就可以按它开发。约定正文落在 `docs/project-service.md`。

### 通用约定

1. 请求和响应都是 UTF-8 的 JSON，字段名用 snake\_case，响应带 `Cache-Control: no-store`。
2. 资源读回统一是 `{kind, id, data, artifacts}`。`data` 是后端命令输出的原样 JSON，服务不改名、不删字段、不补值。网页忽略不认识的字段，缺的键按 null 处理。
3. 各种 ID 都是不透明字符串，网页不解析也不拼接。日志句柄有两种格式（作业的 `<32 位十六进制>.stdout` 或 `.stderr`，资源的 `art-…`），也都当不透明字符串。
4. 网页只提交业务字段。仓库、数据目录、运行目录、可执行文件都在服务启动时决定，动作里不能改。
5. 业务判断以领域字段为准：读回里的 `next_action`、`phase`、`verification`、`current_eligible`，以及阶段的门槛字段（直接模式 `candidate_verified`、`tests_passed`、`review_satisfied`；分派模式另有 `split_verified`、`can_integrate`、`leaves[].unmet_dependencies`）。服务只检查参数结构和 ID 归属，其余交给 CLI，CLI 的拒绝通过作业返回。
6. 网页把后端返回的所有文本（需求、模型输出、日志、diff）按纯文本显示，不当作 HTML 渲染。
7. 本文没写到的服务行为以 `docs/project-service.md` 和代码为准。`docs/workspace-api.md` 里「只有 `environment.refresh` 一个作业动作」「409 只表示提供方忙」两处已过时，由桥一侧顺手改掉。

### 启动与页面托管

1. 启动命令是 `uv run python -m multi_agent.web --repository <仓库> --data-dir <数据目录>`，可选 `--port`（默认 0，自动选空闲端口）、`--codex-bin`、`--claude-bin`、`--tool-directory`（可多次）、`--runtime-read-path`（可多次）。标准输出只有一行 `http://127.0.0.1:<端口>`。
2. 只监听 IPv4 的 `127.0.0.1`。每个请求的 Host 必须正好是 `127.0.0.1:<端口>`，用 `localhost` 打开会得到 403 `invalid_host`，所以页面一律从打印出的地址打开。POST 带 Origin 时必须等于这个地址，不带也放行。不返回任何 CORS 头。
3. 数据目录要在仓库及其 worktree 之外、属于当前用户、权限私有。服务用 `<数据目录>/web-environment/owner.lock` 独占数据目录，同一数据目录只能起一个服务。服务启动时会把已有的 `reviews.sqlite3` 升级到新结构，打开旧存档前要先复制一份。
4. （补 1）页面托管：新增 `--frontend-dist`。不给时，启动入口取工作台自身源码目录下的 `frontend/dist`，不取 `--repository` 指向的目标仓库，免得把目标仓库里的文件当成同源页面托管。`/api/` 以外的 GET：有对应文件就返回文件，解析后的路径必须在该目录内；`/assets/` 下找不到回 404；其他路径返回 `index.html`（带 `Cache-Control: no-cache`），网页可以用路径路由。目录不存在时 `/api` 照常工作，`/` 回 404 纯文本，写明构建命令。现在服务对 `/api` 以外的路径一律回 404 JSON，服务对象不带页面目录时（单元测试里）仍是这样。
5. 页面只请求同源地址，不用 CDN、外部字体、统计脚本和 Service Worker，断网可用。
6. 开发模式：网页的开发服务器把 `/api` 转发给服务，目标地址从环境变量 `BRIDGE_URL` 读，转发时把 Host 改成 `127.0.0.1:<端口>`，Origin 改成服务地址或去掉。服务不为开发模式放宽检查。
7. 模拟模式：网页另有一个不需要服务的启动方式，只回放样例和一条固定的作业时间线，不实现任何业务规则。

### 端点和对象

| 请求 | 查询或请求体 | 成功响应 |
| --- | --- | --- |
| `GET /api/workspace` | 无 | 200 `workspace` |
| `GET /api/runs` | 可选 `kind` | 200 `{items:[{kind, id, label, parent_id, updated_at}]}` |
| `POST /api/jobs` | `{action, args}` | 202 `{job_id, state:"queued"}` |
| `GET /api/jobs`（补 2） | 无 | 200 `{items:[job]}`，最近 50 个，含未结束的 |
| `GET /api/jobs/{job_id}` | 无 | 200 `job` |
| `POST /api/jobs/{job_id}/cancel` | `{}` | 202 `{job_id, state:"cancelling"}` |
| `GET /api/resources/{kind}/{id}` | 见下方说明 | 200 `{kind, id, data, artifacts}` |
| `GET /api/diffs/{kind}/{id}` | kind 为 `task`、`integration`、`snapshot`；（补 5）可选 `against=parent` | 200 diff |
| `GET /api/snapshots/{id}/file` | `side`、`path` | 200 `{side, path, text, oid, mode}`，二进制文件 `text` 为 null |
| `GET /api/artifacts/{artifact_id}` | 可选 `offset`、`limit`（字节，1 到 65536，默认 65536） | 200 日志的一页 |

- 资源有 13 种：`project`、`consultation`、`goal`、`project-plan`、`project-stages`（id 是计划的 `plan_id`）、`stage`、`plan`、`task`、`task-test`、`task-review`、`integration`、`review`、`snapshot`。`history=1` 只能用于 `plan`、`task`、`task-review`、`integration`、`review`。`task-test` 必须带 `implementation_attempt`，可选 `test_attempt`。其他查询参数一律 400。
- `project` 不列咨询和阶段：阶段要按计划读 `project-stages`，咨询从 `goals[].consultation` 找；没被采纳的咨询只能从作业结果或 `runs` 找到。
- 带 `artifacts` 的只有 `project-plan`（计划日志）、`consultation`（席位日志）、`review`、`task-review`、`snapshot`（冻结的测试输出）、`integration`（各次测试日志）和 `task-test`。Sol、Terra、Sonnet 和审核席位的会话日志没有入口，见「需要后端改的地方」。
- `workspace` = `{repository, target_branch, head, read_only, presets:{source, models, roles, rules}, environments:{codex, claude}}`。游离头时 `target_branch` 为 null，空仓库时 `head` 为 null，`read_only` 恒为 false。
- `presets.roles` 有 6 个：advisor、planner、stage\_lead、implementation、fallback、review，每个是 `{id, label, families, candidates:[{family, provider, model, efforts, source, effort_source}]}`。Codex 的候选要等第一次 `environment.refresh`（provider 为 codex）成功才出现，所以首次打开时 Sol、Terra、Astra 的选择器是空的，网页要提示先检查环境。Luna 和 Haiku 被过滤掉。
- 选择器和动作参数之间有三处要网页翻译：候选里 Claude 的 provider 写 `claude`，实施、后备和子卡执行者要传 `claude-code`；`stage_lead` 对应动作参数 `sol`，只传 `{model, effort}`；实施角色里有 Sol，但子卡执行者只能选 Terra 或 Sonnet。
- `presets.rules` 是按当前 HEAD 读的项目规则（`status`、`protected_paths`、`implementation[]`、`default_implementation`、`task_types` 等）。测试命令名不在这里，`task.test` 的 `commands` 取任务读回里冻结的规则。`environments` 里是最近一次成功的环境检查，失败的检查只记在那个作业上。
- `runs` 只登记作业结果里出现过的 ID。`label` 恒等于 ID，`updated_at` 是最近一次提到它的作业的结束时间，不是领域更新时间。不登记的有：`task-test`、`project-stages`、自动返工前的原审核轮、修订集成和源集成的父子关系（补 7）。在终端里用 CLI 建的记录不会出现在列表里。
- diff：`task` 是卡的基线到当前候选，`integration` 是目标基线到候选，`snapshot` 是冻结的审核输入。没有已核验候选时仍回 200，`diff` 为 null，带 `unavailable_reason`，网页看这个字段而不是状态码。`test_change_paths` 只有集成审核快照有值。修订候选相对父候选的增量现在拿不到（补 5）。网页自己解析 diff 文本，要处理重命名头、二进制文件行和带引号转义的路径。
- 日志分页每页单独按 UTF-8 解码，坏字节换成替换字符，中文跨页时边界上会出现乱码。`next_offset`、`byte_count`、`sha256` 的含义以 `docs/project-service.md` 为准。
- `snapshot` 读回返回整份审核输入，包括全部文件文本，最大可达 64 MiB，只在需要时请求。粘贴 diff 生成的快照没有仓库，现在读不到（404）。

### 作业

状态走向：`queued → running → finished`；取消时是 `running → cancelling → finished`。服务重启时，未结束（`queued`、`running`、`cancelling`）的作业变为 `interrupted`。

1. 作业对象是 `{job_id, action, state, exit_code, result, error, resources:[{kind, id}], artifacts}`。`artifacts`（stdout、stderr 两个句柄）只在 CLI 退出后出现，运行中没有实时日志。（补 2）增加 `args`（文本字段只留长度）、`created_at`、`started_at`、`finished_at`、`cancel_requested_at`。
2. （补 3）一次只跑一个 CLI 作业：已有未结束（`queued`、`running` 或 `cancelling`）的 CLI 作业时，`POST /api/jobs` 回 409 `busy`，`error.details.active_job_id` 给出它的 ID，服务不排队。`environment.refresh` 不受此限，但同一提供方同时只能检查一次（409 `environment_busy`）。现在的服务允许两个作业同时跑，第二个抢不到仓库锁会以退出码 2 失败，第三个连同环境检查一起排队。
3. `error` 为 null 不代表成功。stdout 只要是一个 JSON 对象就存为 `result`，不管退出码。网页把 `exit_code` 和读回的领域字段放在一起看：
   - 0：成功。
   - 1：命令跑完了但结果不满足（未核验、审核要返工、集成冲突等），多数带 JSON；未捕获的异常也会是 1 且没有 JSON。
   - 130：被中断，多数带 JSON；`task.test` 和键盘中断时没有 JSON。`project.plan` 被取消时是 1，`result.error.failure_category` 为 `cancelled`（推断，待实跑确认）。
   - 2：参数错误或业务拒绝，只有 stderr，没有 JSON。例如接受资格不够、阶段模式不符、对已有实施再次 `task.run`、没有登记测试命令、仓库锁被占。
4. `error.code`：`cli_failed`（非 0 且没有 JSON）、`cli_cancelled`（130 或 SIGINT 且没有 JSON）、`invalid_cli_output`（退出 0 但输出不是 JSON 对象）、`cli_launch_failed`、`cli_io_failed`、`state_write_failed`、`service_interrupted`（重启时未结束）。`result` 为 null 时原因只在 stderr 日志里，网页读它的末尾显示（补 9 会把末尾直接放进作业记录）。
5. `resources` 是从 `result` 里按固定键找出的 ID，`result` 为 null 的作业没有 `resources`。新建类动作的 ID 也只在结果里，失败时网页从动作参数和上一级资源重新读。
6. 取消只在 `running` 时可以：回 202 `{job_id, state:"cancelling"}`，作业状态变为 `cancelling`，服务向 CLI 发一次 SIGINT。`queued`、`cancelling` 和已结束的作业回 409 `job_unavailable`，网页只在 `running` 时显示取消按钮。CLI 退出后作业照常结束为 `finished`，退出码多为 130。`cancelling` 期间网页显示「已请求取消」，作业结束后按退出码和领域状态显示「已取消」；补 2 的 `cancel_requested_at` 记下请求的时间。
7. 服务只发一次 SIGINT，不强杀。按 Ctrl-C 停服务时会对在跑的作业各发一次 SIGINT 并等它们结束。服务崩溃时 CLI 进程可能继续运行，重启后标为 `interrupted` 的作业仍可能在改领域状态，网页先轮询领域资源，再提供恢复操作。
8. 作业记录保存在 `<数据目录>/web-environment/state.json`，重启后已结束的作业、日志句柄和 `runs` 列表都能读回。
9. 重复提交：只有 `project.stage.start`（同一计划、同一阶段）和已领取子卡的 `project.stage.leaf` 不产生新工作。其余动作重复提交会新建一份（咨询、目标、计划、审核轮、集成）或以退出码 2 失败。网页提交后在作业结束前禁用按钮。
10. 轮询节奏：运行中的作业每 1 秒读一次；作业运行期间只读不抢锁的资源，最多每 5 秒一次；其余等作业结束后读一次。
11. `environment.refresh` 在服务进程内执行，超时 30 秒，`exit_code` 恒为 null，没有 `artifacts`，不能取消。网页不在页面加载时自动发起，Codex 候选为空时提示用户点一次。

### 读回与仓库锁

后端的实施、测试、审核、集成作业以不等待的方式抢仓库的执行锁（`<git 公共目录>/multi-agent-executor.lock`），抢不到立刻以退出码 2 失败，而且一次作业中间会放锁再抢好几次。下表里「抢锁」的读取也会短暂抢同一把锁：读取撞上作业，得到降级数据；作业撞上读取，作业直接失败，包括模型已经跑完、正要冻结候选的时候，也可能让作业的自检读成未核验、打断自动返工。

| 读取 | 抢锁 | 作业期间撞锁时的表现 |
| --- | --- | --- |
| `task`、`task-review`、`integration` | 是 | 仍回 200，但 `verification` 变成未核验，错误原文在 `source_errors` 或 `verification_errors` |
| `task-test` | 是 | 同上；它的测试日志句柄消失，读日志回 404 |
| `stage` | 是 | 门槛字段（`candidate_verified`、`tests_passed`、`review_satisfied`、`can_integrate`）读成 false |
| 分派子卡的 `plan`（上游已有集成时） | 是 | 同 `task`。网页从 ID 分不出来，作业期间把 `plan` 都当抢锁处理 |
| `task`、`integration` 的 diff，以及上面几类资源的日志 | 是 | 任务 diff 带 `unavailable_reason`；日志可能 404 |
| `project.stage.integrate` 提交前的检查 | 是 | 409 `job_unavailable`，提示子卡未全部核验，可能是误报 |
| `workspace`、`runs`、作业和作业日志、`project`、`consultation`、`goal`、`project-plan`、`project-stages`、`review`、`snapshot`、快照文件和快照 diff | 否 | 随时可读 |

1. 规则（11 月 18 日已确认，19 日按新后端扩大范围）：有 CLI 作业未结束时，网页不发上表中抢锁的读取。（补 3）服务也同样拦住：作业未结束期间这些读取不碰锁，直接回 200 并带 `lock_busy: true`。资源为 `{kind, id, data:null, artifacts:[], lock_busy:true}`；diff 保留现有的键，`diff` 为 null，另带 `unavailable_reason` 和 `unavailable_code:"lock_busy"`；日志页保留现有的键，`text` 和 `next_offset` 为 null。`unavailable_code` 为 `lock_busy` 只来自服务自己的这道拦截，不从后端的错误文字推断。网页保留上一次读到的内容并标出读取时间，没有就显示「作业运行中，结束后可读」。
2. 两个抢锁读取同时发也会互相降级，所以没有作业时网页也逐个发，不并发。
3. 作业期间看进度：审核席位读不抢锁的 `review`（任务审核轮也能用这个种类读）；需求咨询、项目计划、阶段列表直接读；实施和测试的进度只能等作业结束。
4. 别的进程占锁时（例如同时在终端对同一仓库跑 CLI），后端返回降级结果，错误原文在 macOS 上大约是 `[Errno 35] Resource temporarily unavailable`（推断）。服务原样透传，网页如实显示「仓库被占用，结果未核验」，不当成最终结论。已知限制：工作台运行期间不要在终端对同一仓库另跑会改状态的 CLI。
5. 读回的状态码：还没有数据库、ID 不存在或属于别的仓库回 404；种类、ID 格式、查询参数不对回 400，Git 读取出错也是 400；数据库错误回 500 `workspace_unavailable`。网页把 500 和网络错误当可重试。
6. 读取只碰执行锁。规划作业另有数据目录里的规划锁，读取不碰它。`project.consult`、`project.confirm`、`project.plan`、`project.revise` 不抢任何文件锁。

### 动作参数

`role = {provider, model, effort}`。provider：咨询、计划、卡片复核、审核席用 `codex` 或 `claude`；实施、后备、子卡执行者用 `codex` 或 `claude-code`。model 必须是 `gpt-<版本>-astra|sol|terra`（codex）或 `claude-fable|opus|sonnet-<版本>`（claude）。effort：codex 取 low、medium、high、xhigh、max、ultra，claude 取 low 到 max。服务只检查格式和家族，不查模型目录，模型不支持的档位会在作业里失败。

| action | 必填 | 可选 | 角色限制和说明 |
| --- | --- | --- | --- |
| `environment.refresh` | `provider`（codex 或 claude） | 无 | 在服务进程内执行 |
| `project.consult` | `baseline`、`original_goal`、`advisors`（1 到 2 位） | `project_id` | Astra、Fable；两位时提供方必须不同。依次进行，每位 300 秒 |

| `integration.rework` | `integration_id`、`round_id` | 无 | 每条谱系只能一次，第二次以 `budget_exhausted` 拒绝 |
| `integration.rebase` | `integration_id` | 无 | 只在目标分支移动过（`target_is_current` 为 false）时可用 |
| `integration.accept` | `integration_id`、`round_id` | 无 | 不满足条件时退出码 2，原因只在 stderr |

- 服务只检查参数的键、类型、席位数、家族和 ID 归属（属于本仓库）。审核轮和集成是否配套、命令名是否已登记这类规则由 CLI 判断，失败表现为退出码 2 的作业。`round_id` 一律取对应资源里最后一轮的 ID。
- `seat_keys` 取读回里的 `seats[].key`，网页不自己拼。
- 动作上没有 `timeout`、`grace`、`max_attempts`：咨询和计划 300 秒，实施、测试、审核 180 秒，测试输出上限 8 MiB，实施预算 2 次。第一版沿用这些默认值。
- T-0062 里的 `plan.create`、`plan.retry`、`review.freeze`、`review.run`、`review.retry`、`review.confirm` 和只读打开（`--read-only-database`）现在都没有，按第 6 项的决定后移（补 10）。

### 错误

错误体是 `{error:{code, message}}`，（补 3）扩展为 `{error:{code, message, details}}`，`details` 可以省略。网页按 `code` 显示中文提示，`message` 放在详情里。

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `invalid_request`、`unknown_action`、`invalid_provider` | 请求结构、查询参数或动作参数不对；Git 读取出错也会是 400 |
| 403 | `invalid_host`、`invalid_origin` | Host 不是 `127.0.0.1:<端口>`，或 Origin 不符 |
| 404 | `not_found` | 资源、作业、日志、快照文件不存在，或 ID 属于别的仓库 |
| 409 | `environment_busy`、`job_unavailable`、（补 3）`busy` | 同一提供方正在检查；作业不能取消、阶段还不能集成、服务正在关闭（三者共用 `job_unavailable`，按上下文区分）；已有作业在跑 |
| 500 | `workspace_unavailable` | 文件或数据库错误 |
| 501 | `invalid_request` | 不支持的方法，包括 OPTIONS |

POST 请求体必须是 `application/json`、固定长度、1 字节到 8 MiB，不接受分块传输。POST 以及 `workspace`、`jobs`、`diffs` 带查询参数一律 400。

### 安全

1. 只监听 `127.0.0.1`，Host 和 Origin 检查见「启动与页面托管」，不返回 CORS 头。
2. 浏览器不能提交路径、可执行文件或命令参数。子进程用参数数组启动，不经过 shell，stdin 为空，单独的进程组；文本输入先写成数据目录里的私有文件再传路径。
3. 日志只能通过已登记的句柄读，快照文件只能按快照里记录的 `side` 和 `path` 读。
4. 资源和动作里的 ID 都核对是否属于启动时绑定的仓库，不属于的一律 404。

## 需要后端改的地方

下面几条不在桥的范围内，建议另开一张后端任务卡。网页第一版不依赖它们，靠桥的串行保护和网页一侧的显示规则绕开。

- 读取以不等待的方式抢执行锁，作业抢锁又不重试，一次读取就能让作业失败。桥只能挡住网页自己的读取，终端里的 CLI 仍会撞上。根本办法是读取不抢执行锁，或者作业抢锁时短暂重试。
- 退出码 2 的业务拒绝只有 stderr 文字，没有 JSON；部分未捕获的异常以退出码 1 结束，也没有 JSON。网页只能显示英文原文。
- 咨询席位进程在中途被强杀，记录会一直停在 running，没有对账路径；其他时刻收到 SIGINT 也可能留下这样的记录（推断）。
- 子卡的卡片复核模型不能单独选，只能在领取阶段时定下。
- Sol、Terra、Sonnet 和审核席位的会话日志没有读取入口。
- 粘贴 diff 生成的快照没有仓库字段，过不了归属检查（只在补 10 要做独立审核时才需要）。

## 样例与离线联调环境

离线联调环境是两个模块唯一互相调用的地方，由桥一侧做（补 6）。

1. 入口是 `uv run python tests/unit/web_support/offline_env.py --scenario <名称> --port 0 [--frontend-dist <目录>]`。每次启动新建临时仓库和数据目录，`HOME` 和 `CODEX_HOME` 也指向临时目录，带假模型程序启动服务，标准输出第一行是服务地址。SIGUSR1 硬停服务和它的 CLI 子进程，再用同一批临时目录、同一端口重启，用来得到 `interrupted`；SIGHUP 正常重启（可选）；每次重启后重新打印地址。只有 Ctrl-C（SIGINT）停止并清理。
2. 场景至少有：`accept`（从目标走到接受，含一个直接阶段和一个两张子卡的分派阶段）、`rework`（首轮审核报一条带文件和行号的阻塞意见，返工后通过）、`dual-partial`（双席审核一席首次失败，补跑成功；其中一席的假程序不报告模型，读回为 null）、`cancel`（实施中途取消，作业经 `cancelling` 结束为 `finished`，退出码 130）。
3. 假程序按状态自己判断当前角色，codex 和 claude 各一个，启动一次就能从页面走完全程。现有的 `tests/unit/runtime_fakes/` 要测试代码在步骤之间改角色文件，还只接受 `high` 档，不能直接用。假模型目录包含完整家族（含 Luna 和 Haiku，用来验证过滤），其中至少一个型号支持 `low`，假程序也接受 `low`；假程序路径固定，录下的样例才稳定。
4. 假模型报告的模型名是占位值（例如 `echo-not-evidence`），页面照样按报告值显示，正好用来检查「不拿请求值顶替」。
5. 每个场景录一份真实响应，存到 `docs/web-api/samples/<场景>/`：`index.json` 按顺序列出 `{seq, method, path, query, request_body, status, response_file}`，响应体放在 `NNN.json`，作业轮询只留状态变化的几次。保存前把 ID、提交 SHA、sha256、时间、临时路径和端口按首次出现的顺序换成稳定的占位符，`art-` 句柄先解码、替换再编码；重录时比较规范化之后的内容。另外录下页面要处理的几种状态：作业运行中对 `task`、`stage`、一个 diff 和一个日志页的 `lock_busy` 读取；资格不够时提交 `integration.accept` 得到的退出码 2、`result` 为 null；硬停重启后的 `interrupted` 作业。网页的模拟模式和组件测试直接读这些样例。录制脚本放在 `tests/unit/web_support/`，样例不手改，格式和规范化规则写进 `docs/project-service.md`。
6. `docs/project-service.md` 末尾加一节，逐场景列出页面上要填的目标、基线、模型名、测试命令名和预期结果。网页的端到端脚本只通过这条命令和 `/api` 与环境交互。
7. 现成的起点：`tests/unit/test_web_project_flow.py` 已经在进程内用假程序跑通了项目流程，离线环境可以从它改出来。

各自的检查：

- 桥：每个补齐项有端点测试；现有 `test_web_*` 全部仍通过；样例能由录制脚本重建。
- 网页：类型定义与样例一致；模拟模式直接读样例；组件测试用样例渲染每一种状态，包括 `lock_busy`、退出码 2 没有 JSON、`interrupted`、报告值为 null。
